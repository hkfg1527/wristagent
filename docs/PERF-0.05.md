# 0.05 性能实测

> 方法、数字与局限都写在这里。**没有做的测量不列进来**，没有复现步骤的数字不算数。

## 设备与方法

- 设备：TicWatch Pro 5（`C101X35122973`），466×466，**屏幕只有 60Hz**（`dumpsys display` 报 `fps=60.000004`），
  所以一帧预算 16.67ms。
- 安装包：`assembleRelease` 产出的 release APK（版本见 `wear/build.gradle.kts`），不是 debug 包。
- 采集：`adb shell dumpsys gfxinfo <pkg> reset` → 用 `adb shell input swipe` 脚本化滑动 → `dumpsys gfxinfo`。
  每个场景固定 **10 次滑动**（5 次向上 300ms、5 次向下 300ms，间隔 450ms），每次滑动 210px。
- 判据用平台自己的直方图（`Janky frames (legacy)` 与 50/90/99th percentile），不自己造公式。
- **每种风格都是一次冷启动 + 一次进入设置页**，所以数字里含首帧建树的成本；这是"用户第一次滑"的真实成本，
  但它不是稳态数字，见文末局限。

## 结果

| 场景 | 渲染帧 | Janky（legacy） | p50 | p90 | p99 | GPU p50 / p90 |
|---|---|---|---|---|---|---|
| **聊天页**（对话列表滑动） | 79 | **2（2.53%）** | 12ms | 15ms | 17ms | 5 / 7ms |
| 设置页 · 终端档 | 277 | 26（9.39%） | 13ms | 17ms | 25ms | — |
| 设置页 · 大卡片档 | 308 | 99（32.14%） | 16ms | 28ms | 73ms | 3 / 7ms |
| 设置页 · 方角档 | 286 | 215（75.17%） | 22ms | 31ms | 53ms | — |
| 设置页 · 气泡档（默认） | 285 | 242（84.91%） | 26ms | 34ms | 53ms | 5 / 10ms |


## 两次对照实验（同一台表、同一段脚本）

为定位默认风格那 70~85% 的掉帧，做了两次"拆件"实验，各只改一处、跑同一段滑动：

| 变体 | Janky | p50 | 结论 |
|---|---|---|---|
| 气泡档（原样） | 70.9% / 84.9% | 21 / 26ms | 基线 |
| **不画气球背景路径**（跳过 `buildGroupPath` + `drawPath`） | **33.0%** | **15ms** | 背景路径约占总掉帧的一半 |
| **把行内缩放固定成 1**（保留 position 跟踪与图层） | 43.6% | 18ms | 行内缩放+图层约占一半 |
| **把行内缩放改成绘制阶段 `drawWithContent { scale(...) }`**（去掉图层与 state 写入） | **90.8%** | **30ms** | **反而更慢 —— 假设被推翻** |

最后一行很重要：原本以为"每帧写 snapshot state"是主因，实测把 state 写入整个去掉、改成绘制阶段缩放后，
掉帧从 85% 涨到 91%。这说明 `graphicsLayer` 的图层缓存是在**帮忙**（内容画一次、之后只做变换），
把这些内容每帧重画进绘制指令反而更贵。**"state 写入是主因"这个判断是错的，已撤回。**

## 结论（修正版）

1. 聊天页达标（2.53%），不是问题所在。
2. 设置页默认风格重，主要是**整页气球轮廓每帧重建 + 重填一次**（约一半），另一半分布在行内容绘制上。
3. 想真正解决，需要 Perfetto 的 CPU 火焰图来分辨"路径构建"与"渐变填充"各占多少 —— 只靠
   `gfxinfo` 的直方图分不出来，继续盲试只会像上面那次一样改反。

## 局限（必须一起读）

- 每种风格只跑了 1~2 次，样本量小；同风格两次之间差异最大到 60 个百分点（方角档 75.17% vs 7.58%），
  说明**落点内容**对结果影响很大，上面的排序只能当量级参考。
- 没有 Perfetto 火焰图，"瓶颈在路径重建"是从拆件实验反推的**推断**。
- 首帧建树成本混在每次冷启动的数字里。
